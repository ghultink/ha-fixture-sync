Tech docs — smart related items, end to end

Everything you need to wire up smart related items on your own publication: how the player picks what to show, what a smart playlist really is, the data-source contracts you can hook into, and the embed-side options.

1. How the player picks "related items"

For every main-roll clip, the player walks a 5-step priority ladder when assembling its post-roll panel:

PrioritySourceWhat triggers it
1External listHost called player.setRelatedItems([…]) (or setRelatedClips) — see scenario ④.
2Clip-level cliplistThe mediaclip has one of relatedItemsListId, relateditems, gerelateerdeitems, relatedcliplist, exitscreen, exitscreenitems set.
3Playout-level cliplistThe playout has exitscreenItemsListId set — the path used by ①, ②, ③.
4Tag searchNo cliplist available — fallback: a weighted search on the clip's cat tags and title words.
5Latest publishedLast resort: most recently published items in the publication.

Steps 2 and 3 hit the SAPI search endpoint:

GET {publication}/json/search?cliplistid={id}&filterbyusetype=all&limit=15&…

If the cliplist has allowDatasource: true, the player does not trust the static filter values stored on the cliplist. Instead it resolves each filter's datasource at runtime — reading the host page's URL, the visitor's storage, etc. — and then re-issues the search with the resolved values:

GET {publication}/json/search?filterset=[resolved]&sort=…&limit=…

One step earlier — Suggests (§ 5c). The 5-step ladder above is about which items fill the end-screen panel — it assumes the main clip is already decided (by the embed script's contentId). Suggests works in front of that: with useSuggest: true on the cliplist or ?useSuggest=true on the embed URL, the Suggest helper runs before _objectInit and replaces the bootstrap's clipData with whatever the Blue Billywig search engine ranks first. The remaining results pre-fill clipListData.items, so the same 5-step ladder then renders the end-screen panel from those already-fetched items.

2. Anatomy of a smart playlist (cliplist)

A "smart" cliplist (created in the Blue Billywig OVP library) has:

  • listtype: "dynamic"
  • filterType: "filters" (the alternative is "solr" — raw query)
  • allowDatasource: "true" — this is the toggle that enables the plug icon next to each filter value in the Blue Billywig OVP and tells the player to defer value resolution to runtime.

The persisted JSON (this demo's QueryString cliplist, abridged):

{ "listtype": "dynamic", "filterType": "filters", "allowDatasource": "true", "limit": 15, "sort": "published_date desc", "filters": [ { "filters": [ { "id": "qstopic", "type": "search", // entity scope "field": "cat", // OVP field name "operator": "containsAnyOf", "value": "recipes", // hard-coded fallback "datasource": { "sourceType": "QueryString", "sourceValue": "topic", "defaultValue": "recipes" } } ] }, { "filters": [ { "id": "ccgate", "type": "search", "field": "cat", "operator": "containsAnyOf", "value": "creative-commons" // static gate — demo content only } ] } ] }

Filter groups are AND-ed together; filters inside a group are OR-ed. The second group above is a static content gate that keeps this demo bounded to its CC0 video pool.

Gotcha — the content preview on the Playlists page does not update with dynamic filter settings. Dynamic filters are evaluated per clip, so the playlist's own preview list (which has no clip context) shows the static fallback, not the resolved result. To verify a dynamic filter, preview or embed a clip on a page that has the corresponding input present (URL parameter, localStorage value, meta tag, …) and watch the post-roll strip.
Recommendation — pair dynamic filters with a default filter set. Add a second filter group (or a static value alongside the datasource) so the playlist still returns something usable when the dynamic input is missing or broken.

4. Data-source types

Each filter can carry one datasource object. Contract:

{ sourceType: 'QueryString' | 'LocalStorage' | 'JavaScript' | 'PlainText' | 'DatafeedValue' | 'WidgetProperty', sourceValue: string, // key / script / "id:column" defaultValue: string // fallback when source resolves to empty }

QueryString

Reads from the request parameters the player sees. With JS-embed, the player runs same-origin in the host page, so query parameters on the host page's URL are visible. Values that look base64-encoded are auto-decoded.

"datasource": { "sourceType": "QueryString", "sourceValue": "topic", "defaultValue": "recipes" }

LocalStorage

Reads from a per-player storage layer. Important: this is not the browser's global window.localStorage. The host page can write to the player's store via the public API:

// Set BEFORE the player script loads window.bluebillywig = window.bluebillywig || {}; window.bluebillywig.onPlayerAdded = (player) => { player.setLocalStorageItem('bb_demo_topic', 'parenting'); };

Filter side:

"datasource": { "sourceType": "LocalStorage", "sourceValue": "bb_demo_topic", "defaultValue": "recipes" }

Combine with window.localStorage on the host side if you want the preference to outlive a single page: persist there, then mirror into the player on every onPlayerAdded callback.

JavaScript

A small expression evaluated by the player at filter-resolution time. The returned value becomes the filter input. Use this when the right value is computed from page state — e.g. an HTML meta tag, a JS global, derived session info.

"datasource": { "sourceType": "JavaScript", "sourceValue": "(function(){var m=document.querySelector('meta[name=\"x-bb-topic\"]'); return m?m.content:'';})()", "defaultValue": "recipes" }

Macros are pre-substituted inside sourceValue / defaultValue: {{querystring.X}}, {{localstorage.Y}}, {{mediaclip.Z}}, {{playout.Q}}, {{player.P}}, {{asset.A}}.

PlainText (UI label: "Text with macro")

A literal value with macro expansion (same macro set as JavaScript). The macros expand per clip at the moment the filter is resolved — so {{mediaclip.length}}, {{mediaclip.cat}}, {{querystring.cc}}, etc. all become live values. Useful for composite keys: country_{{querystring.cc}}.

DatafeedValue

Points at a Datafeed (CMS-managed CSV-like table managed in the Blue Billywig OVP). Format "<feedId>:<columnKey>". The helper supports condition columns so different rows can fire based on the player's LocalStorage state.

WidgetProperty

Reads a property off a widget on the page (interactivity editor). Mostly used inside interactive videos.

5. Bypassing the cliplist (scenario ④)

If your site already has its own recommendation engine, just hand the player a finished list. Sanity-check on the first item: it needs at minimum id, type, title, deeplink. Pass anything thinner and the player enriches by ID via a SAPI lookup.

window.bluebillywig = window.bluebillywig || {}; window.bluebillywig.onPlayerAdded = (player) => { player.setRelatedItems([ { id, type: 'MediaClip', title, deeplink /*, thumbnail, length, ... */ }, // ... up to 15 ]); }; // to release control back to the cliplist later: // window.bluebillywig.players[0].setRelatedItems(null);

5b. Bonus: AI-suggested items (scenario ⑤)

The AI-suggested scenario is a thin variant of scenario ④: instead of the host site hand-picking the items, it asks an in-browser AI agent to do it. The smart bit is that the entire reasoning step can run on the visitor's device — no API keys, no server round-trip, no third-party tracking.

Which browser AIs are actually available?

Two shapes of on-device Prompt API are currently in the wild, both exposing a small instruction-tuned language model bundled with the browser:

SurfaceBrowserStatus (Q2 2026)Notes
window.LanguageModelChrome ≥ 138 (stable on most channels)shipping behind an availability gate (~Gemini Nano)Recommended path. ~ a few hundred MB one-time model download per profile.
window.ai.languageModelEarlier Chrome / Edge previewskept for backwards compatibilitySame prompt-style API, slightly older shape.
(neither present)Firefox, Safari, older Chrome—Fall back to a chat-tab paste workflow (see below).

Detection + capability check

Treat the surface as untrusted feature-detection: presence ≠ readiness. The model file may still be downloading, or the user may have opted out of AI features.

async function getSession() { if (typeof window.LanguageModel !== 'undefined') { const avail = await LanguageModel.availability(); // 'readily' | 'available' | 'after-download' | 'no' if (/(readily|available|download)/i.test(avail)) { return await LanguageModel.create({ initialPrompts: [{ role: 'system', content: 'You return strictly machine-readable JSON. No prose, no code fences.' }] }); } } if (window.ai?.languageModel) { return await window.ai.languageModel.create({ systemPrompt: 'You return strictly machine-readable JSON. …' }); } return null; // caller falls back to chat-tab flow }

What we ask the AI for

Don't send the whole catalogue. On-device models have small context windows; a real publication has thousands of clips. Use the AI as a topic classifier, not as the search engine — the Blue Billywig search engine already knows everything.

The prompt gives the model two things and asks for one:

  1. The article theme, in 1–2 sentences. Typed by the editor, derived from a CMS field, or computed from page content.
  2. The list of buckets the site organises content into — just names + a one-line description. Four buckets in this demo; in a real deployment, maybe a dozen tags from your taxonomy.
  3. Strict output instructions: a single JSON object, { topics: [...], reason: '...' }, picking 1–3 of the valid buckets, no prose, no code fences.
You are categorising an article so a video player can fetch relevant follow-up videos. The site has four content buckets: - recipes — food, cooking, quick meals - real estate — buying / renting / mortgages - parenting — kids, toddlers, family life - gaming — video games, gaming setups ARTICLE THEME / VISITOR CONTEXT: <short free-text theme> Pick 1–3 buckets that best fit the article (in order of relevance). Return ONLY a JSON object — no prose, no markdown fences: {"topics": ["bucket1", "bucket2"], "reason": "max 20 words"} Allowed bucket values: recipes, real estate, parenting, gaming.

Parsing the answer defensively

Even with strict instructions, small on-device models occasionally wrap JSON in ```json … ```, emit a trailing apology, or invent a bucket name. The parser on the host side should be paranoid:

  1. Trim leading/trailing markdown fences.
  2. Slice from the first [ or {; ignore everything before it.
  3. JSON.parse in a try; if it's a bare array of strings, treat it as {topics: ...}.
  4. Whitelist-check every topic against the known bucket list. Drop anything else.
  5. If nothing valid remains, surface the raw response in the UI rather than silently failing.

From AI topics to setRelatedItems — via the SAPI

Once you have a clean list of bucket names, ask the SAPI for clips that match. This is exactly the same search call the cliplist scenarios make, with the topics OR-ed together and the CC-licensed gate AND-ed on:

async function runSapiSearch(topics, limit = 6) { const filterset = JSON.stringify([ { filters: topics.map((t, i) => ({ type: 'search', field: 'cat', operator: 'containsAnyOf', value: t })) }, { filters: [{ type: 'search', field: 'cat', operator: 'containsAnyOf', value: 'creative-commons' }] }, ]); const params = new URLSearchParams({ filterset, sort: 'published_date desc', limit: String(limit), fl: 'id,title,length_int,deeplink_string,cat', }); const r = await fetch(`${PUBLICATION}/json/search?${params}`); const d = await r.json(); return (d.items || []).map(it => ({ id: String(it.id), type: 'MediaClip', title: it.title, deeplink: `${PUBLICATION}/view/${it.id}`, })); } const items = await runSapiSearch(parsedAiResponse.topics); window.bluebillywig.players[0].setRelatedItems(items);

The two-step shape — AI classifies, SAPI searches — means the AI never has to see your full catalogue, and you keep all the production-ready bits of the search engine (relevance scoring, recency, content-protection gates, randomisation, etc.). You can also bypass the AI entirely on cache-hit (same theme → same topics → same SAPI URL).

Fallback path for browsers without an on-device AI

Roughly half of today's visitors don't have a usable window.LanguageModel. The same prompt works in any chat-style web AI; this demo wires up the two most common:

AgentDeeplink shapeNotes
Claude (Anthropic) https://claude.ai/new?q=<url-encoded-prompt> Opens a new chat with the prompt pre-filled. Long prompts work most reliably by also copying to the clipboard before opening the tab (so the visitor can paste with Cmd/Ctrl-V if the query string gets truncated).
ChatGPT (OpenAI) https://chatgpt.com/?q=<url-encoded-prompt> Same pattern. Same clipboard safety-net applies.
Gemini, Copilot, Mistral le Chat, … (no public deeplink → use Copy prompt) The prompt is plain text — every chat tool accepts it. The page offers a one-click Copy prompt button as a generic fallback.

The host page only needs one piece of input back from the visitor: the JSON answer pasted into a textarea. Same parser as the on-device path processes both — so adding another chat agent is just another button.

The alternative integration is a backend proxy: the host site forwards the prompt to a server-side AI with its own credentials and returns parsed picks. Lower visitor friction, but introduces server cost and a third-party data path.

Privacy & safety properties

  • With LanguageModel the prompt and the answer never leave the visitor's device. The host page sees the picks; the BB SAPI sees the resulting setRelatedItems call. No third party.
  • The prompt only contains catalogue metadata + the editor-supplied theme — no visitor identifiers, no cookies, no localStorage.
  • Hallucinated ids are filtered out at the catalogue boundary, so the worst the AI can do is return an empty list (handled like a normal "nothing found" — the cliplist takes over again on the next clip).

6. Embed: JS snippet vs iframe

All five scenarios on this site use the JS-embed snippet:

<div id="player-host"> <script src="https://{publication}.bbvms.com/p/{playoutLabel}/c/{clipId}.js" async></script> </div>

This runs the player same-origin in the host page. Consequences relevant to smart related items:

  • QueryString datasource reads the host page's address bar, so the CMS can drive the filter just by tweaking the article URL.
  • LocalStorage + JavaScript datasources can be primed by the host (via setLocalStorageItem, page DOM, etc.).
  • The public API on window.bluebillywig.players[i] is callable directly from the host — required for scenario ④.

The alternative iframe embed (https://{publication}.bbvms.com/p/{playoutLabel}/c/{clipId}.html) isolates the player but breaks scenario ④ and complicates ② / ③ — the iframe sees a different origin, so it has its own localStorage and its own DOM.

5c. Bonus: Suggests — the player's built-in classifier (scenario ⑥)

What Suggests really does. Every other section on this page is about which clips appear after the main clip ends. Suggests is the only mechanism on the player that changes the main clip itself. The host embeds the player against some bootstrap clip ID; if useSuggest is set, the player throws that anchor away before _objectInit and replaces it with whatever the Blue Billywig search engine ranked first against the host page's metadata. The end-screen panel happens to be filled from the rest of the same search, but that's a side-effect of how Suggests writes clipListData.items, not the headline feature.

Suggests is the Blue Billywig player's own answer to "pick the right clip for this article" — shipped years before LLMs were on the page. It runs in src/helpers/Suggest.js before the player even initialises (Player.js:70-82): if the cliplist has useSuggest: true or the embed script URL carries ?useSuggest=true, the helper scrapes the host page and queries the Blue Billywig search engine (Apache Solr under the hood) for the best matching MediaClip. The first result becomes the main clip the player plays; the rest fill the end-screen.

Signals Suggests reads from the host page

SourceWhat's used
<meta name="keywords">Each comma-separated keyword, AND-ed and OR-ed both ways.
<meta name="og:title"> / <title>Phrase-matched (quoted) + filtered word list.
<meta name="og:description">Filtered word list (stop words stripped per language).
<meta name="og:locale"> / <html lang>Picks the language's stop-word list.
JSON-LD NewsArticle / BlogPosting / WebPageheadline, description, keywords, tag, inLanguage.
location.pathnamePath segments tokenised as fallback keywords.
Cliplist extraSuggestQuery (OVP)Optional escape hatch — a raw search-engine query fragment (Lucene/Solr syntax) or JS returning one, appended to the query, optionally weighted with ^N.

The query Suggests builds

Each part is wrapped in (…)^weight, with the most relevant parts getting the highest weight (descending). Parts are joined with OR. A trailing OR *:*^1 ensures the search always returns something rather than empty. The cliplist's own search query (its filters, flattened) becomes the fq[], so a narrow cliplist becomes a narrow Suggests source — useful for a content-licence gate.

GET {publication}/json/search ?query=(keywords AND-joined)^N OR (keywords space-joined)^N-1 OR "<exact og:title>"^… OR <filtered og:title words>^… OR <filtered description words>^… OR <tokenised URL path>^… OR *:*^1 &fq[]=typeSort:"MediaClip" AND (<cliplist's Solr query>) &limit=10

Per-visitor de-duplication

Suggests keeps a list of clip IDs the visitor has already watched in localStorage.bb_player_viewed_clips (filled from the player's started event, Suggest.js:97-108). On the next page load, the first result whose ID is not in that list wins — falling back to the first result when every candidate has been seen.

How to activate

  • Cliplist-level (the production path): tick Use Suggests on the playlist in the OVP. The OVP makes this mutually exclusive with Allow dynamic filters in the same UI.
  • Embed-level (good for demos): add ?useSuggest=true on the embed script URL. The cliplist attached to the playout still bounds the search via its filter query — make sure that filter is broad enough or the search will return little.

Suggests vs the AI scenario

Both pick a clip from page context. Suggests is a weighted keyword search against the Blue Billywig search engine, runs in every browser, and needs nothing on the page beyond what SEO already adds. The AI scenario classifies first (article → topic bucket) and then uses the cliplist or a SAPI search to look up clips by that label — better when metadata is thin or generic, more dependent on browser capability or on a chat-tab fallback. A real deployment can use both: Suggests as the default, AI when Suggests' top hit has a weak relevance score.
