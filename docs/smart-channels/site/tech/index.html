Tech docs — Smart Channels, end to end

Where the smart-related-items demo wired dynamic filters into the player's post-roll panel, this one wires the same filters into the Channel widget's Cliplist blocks. The cliplist contract is identical; the runtime that resolves it is similar but not the same.

1. Embedding a Channel

One <script>:

<script src="https://{publication}.bbvms.com/ch/{channelId}.js" async></script>

The widget appends its root next to the script tag, attaches a Shadow DOM, and bootstraps from {publication}.bbvms.com/ch/{channelId}.json.

2. The Channel JSON

The bootstrap JSON looks like this (abridged):

{ "appConfig": { "id": "1364", "label": "smart_channel_querystring_demo", "blocks": [ { "type": "FeaturedHeader", "id": "feat-cc-1", "slides": [ { "id": "...", "header": "Quick microwave pasta", "contentType": "mediaclip", "contentId": "7281312" }, /* ... */ ], "config": { "headerVariant": "fullWidth", "imageFitMode": "fit" } }, { "type": "Cliplist", "id": "block-qs", "config": { "header": "Picked for this article (URL-driven)", "contentId": "1778581766079178", // ← the smart cliplist "thumbnailSize": "medium", "playlistLayout": "Carousel" } } ], "colorTheme": "light", "primaryFontColor": "#002837", /* … and styling fields */ }, "publicationData": { /* … */ }, "embedData": { "appId": "1364", "appIndicator": "ch", "baseurl": "..." } }

For each Cliplist block, the Channel widget fetches the cliplist by id and renders its items as a carousel / grid.

3. How the Channel fetches a smart cliplist

For a non-smart cliplist (just a hand-picked list of clips), one call is enough:

GET /papi/search?cliplistid={cliplistId}&allowCache=true

If that response has allowDatasource: true, the widget treats it as a template and re-fires the search with the filter values resolved against the visitor's URL and storage:

GET /papi/search?filterset=<json-array>&sort=…&limit=…

So the per-visitor work is exactly one extra SAPI search call — every other call is shared cache.

4. Supported data-source types in Channels

This is the most important difference from the player. The Channel widget's datasource-resolver currently handles three of the OVP's source types; the rest fall back to the filter's static value:

Source typeIn Channels?How
QueryString✓ supportedReads window.location.search. Base64-prefixed values (b64:…) are auto-decoded.
LocalStorage✓ supportedReads window.localStorage. JSON-quoted values are auto-unwrapped (same convention as the Blue Billywig player's storage engine).
PlainText✓ supportedPass-through to the static value.
JavaScript✗ not supported in ChannelsReturns the filter's defaultValue. (Use a query-string or localStorage instead, primed by the host page.)
DatafeedValue / WidgetProperty✗ not supported in ChannelsSame fallback.

If you need a JavaScript-style "read this from the page DOM" source, keep that logic in the host page and have it write to localStorage or amend the URL before the Channel embed mounts.

5. AI-suggested topics on a Channel

Channels don't expose a setRelatedItems-style escape hatch. So the AI-suggested flow goes one step earlier: the AI is used as a topic classifier, and the host page writes that topic to the URL (or storage) before the Channel mounts. Loop:

  1. Page asks the AI: "Given this article theme, pick 1–2 of these buckets." Same prompt shape as the player demo.
  2. Page parses the JSON answer, validates each topic against the bucket whitelist.
  3. Page navigates to the same URL with ?topic=<top-pick> (or sets localStorage.bb_demo_topic) and lets the page reload.
  4. The Channel mounts, sees the URL / storage, and re-fills its Cliplist block accordingly.

Why a reload? Because the Channel resolves filters once, at mount time. Two ways around it if you don't want a reload:

  • Don't mount the Channel until the AI has answered (defer the <script> insertion).
  • Mount inside a hidden div, then move it into view after answer. Slightly trickier; the reload pattern is the simplest one to get right.
